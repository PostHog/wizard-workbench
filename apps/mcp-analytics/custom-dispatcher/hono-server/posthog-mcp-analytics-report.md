# PostHog MCP Analytics — Instrumentation Report

## Instrumentation path

**Path C — custom HTTP dispatcher (Hono).** The server speaks the MCP JSON-RPC protocol directly over HTTP with no `@modelcontextprotocol/sdk` server object, so `instrument()` is not applicable. `PostHogMCP` from `@posthog/mcp` is used instead, with `captureToolCall` and `captureInitialize` called at the dispatch points.

## Environment variables

These must be present at runtime:

| Variable | Value |
|---|---|
| `POSTHOG_PROJECT_TOKEN` | `phx_API_KEY_IS_HARDCODED` |
| `POSTHOG_HOST` | `https://us.i.posthog.com` |

They are written to `.env`. If you deploy to a hosted environment (Fly, Railway, Heroku, etc.), set them as environment secrets there too.

## What gets captured

Once the server handles requests you will see these events in PostHog:

- `$mcp_initialized` — fired on every `initialize` handshake, with client name and version.
- `$mcp_tool_called` — fired after every `tools/call`, with tool name, parameters, response, duration, and error flag.
- `$exception` — automatically emitted alongside any failed tool call (can be disabled with `enableExceptionAutocapture: false`).

## Manual steps

1. **Verify the `.env` file is not committed.** It should already be covered by `.gitignore` (the wizard-tools `set_env_values` tool ensures this), but confirm before pushing.
2. **Set env vars in your deployment environment** if you host this server anywhere other than locally.
3. **Explore your events** at [https://posthog.com/docs/mcp-analytics](https://posthog.com/docs/mcp-analytics) — the MCP analytics dashboard and event reference are documented there.
4. **Note:** `@posthog/mcp` is pinned to `0.9.1` because it is pre-1.0 and may ship breaking changes in minor releases. Review the changelog before upgrading.
